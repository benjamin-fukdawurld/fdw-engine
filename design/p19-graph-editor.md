# P19 : l'éditeur de graphs

Éditer et déboguer à la souris les trois sortes de graphs du moteur ([roadmap P19](roadmap.md#p19-léditeur-de-graphs)) : les matériaux (P2b, P14), les animations (P6), les comportements (P9). Un seul éditeur, sur le cœur de graph de P6 (`engine-graph`), dans l'éditeur de P18, chaque sorte de graph en **plugin de l'éditeur**.

Ce qui existait : le modèle des documents (`GraphDocument`, nœuds, ports, arêtes), les registres et la validation de chaque sorte (`validateGraph`, `validateAnimationGraph`, `validateBehaviorGraph`), les builders en code, le débogueur des comportements sur l'interpréteur (`BehaviorDebugger`), l'état des machines d'un `Animator` (`state()`), les lignes du code généré des matériaux marquées de leur nœud (`// #n12`), l'historique et les commandes de P15 (`History`, `Command`), les plugins de l'éditeur et leur protocole avec le moteur (P18). Ce qui manquait : la position des nœuds (aucun document n'en avait), l'édition d'un document, le remplacement d'un graph qui tourne (un `BehaviorSystem` et un `Animator` gardaient le leur), le poids des nœuds d'un animator, les fonctions et les macros des comportements, une partie « moteur » des plugins.

## 1. Les choix

| Question                      | Choix                                                                                                                                                                                                                                                                                                                                                                           | Écartés, et pourquoi                                                                                                                                                                                                                                                                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| La bibliothèque du canevas    | **Une écriture maison**, en React (le shell l'est) : les nœuds en HTML, les fils en SVG, une transformation pour le zoom. La position des ports se **calcule** (hauteur d'en-tête et de ligne fixes) : les fils se dessinent sans mesurer le DOM, testables dans jsdom, identiques d'une capture à l'autre                                                                      | **React Flow** (`@xyflow/react`, ~45 ko gzip) : mesure les nœuds dans le DOM (`ResizeObserver`), rien ne se dessine dans jsdom ; ses groupes sont des sous-flows, pas des cadres. **Rete.js** : son propre rendu par plugins (React, Vue, Angular), lourd à typer. **LiteGraph** : un canvas 2D, ni Tailwind, ni accessibilité, ni tests du DOM |
| Où vit le document édité      | **Dans le moteur**, comme le niveau (P18 étape 13) : une `GraphSession` (`@fdw/engine-graph-editing`) tient le document et son `History` ; la page en tient la projection (nœuds et ports résolus, diagnostics, historique) et la change par commandes                                                                                                                          | Dans la page : les nœuds du jeu (les actions des ennemis, des fermetures de `demo-scenes`) et les types inférés des matériaux sont du moteur ; la page devrait les connaître                                                                                                                                                                    |
| Annuler, refaire              | **Les commandes de P15** : chaque édition est une `Command` d'un `History` par session, un instantané du document avant et après (les documents sont des valeurs). Les graphs faits en code n'en ont pas : **`autoLayout`** les dispose en couches à l'ouverture                                                                                                         | Un fichier à côté : deux fichiers à tenir ensemble ; dans `GraphNode` : chaque sorte de graph le verrait                                                                                                                                                                                                                                        |
| Les éditions                  | **Des fonctions pures** d'`engine-graph` (`addNode`, `connect`, `removeNodes`, `pasteFragment`…) sur un `GraphBody` (nœuds, arêtes, layout) : celui du document ou celui d'une de ses fonctions                                                                                                                                                                                 | Des méthodes de la session : non réutilisables ailleurs (un outil en ligne de commande, la page)                                                                                                                                                                                                                                                |
| Les connexions refusées       | **La validation de la sorte de graph** : une connexion qui ajoute une erreur sur son port d'arrivée est refusée, avec le message de la validation (« expected vec3<f32>, got … »). Pendant le glissé, la page colore les ports par une règle simple de la sorte (`accepts`), sans attendre le moteur                                                                            | Une règle de types dans la page seulement : les génériques des matériaux ne se résolvent qu'avec le graph entier                                                                                                                                                                                                                                |

Une seule pour les trois graphs (`graphsExtension`, `@fdw/graph-editor/engine`)                                                                            | Les messages des graphs dans le protocole d'`EditorEngine` : le cœur de l'éditeur connaîtrait chaque plugin                                                                                                                                                                                                                                     |

| Les paquets                   | **`@fdw/engine-graph-editing`** (le moteur : sessions, sortes, cibles, aperçu), **`@fdw/graph-editor`** (la page : le canevas, l'inspecteur, le client ; `./engine` : l'extension), et un plugin par sorte : **`@fdw/editor-plugin-material-graph`**, **`-animation-graph`**, **`-behavior-graph`**                                                                             | Un plugin pour les trois : on ne pourrait en désactiver un ; le canevas dans chaque plugin : trois copies                                                                                                                                                                                                                                       |

| Les source maps               | **Lues dans le code généré** : chaque ligne marquée `// #id` par les trois générateurs ; l'id d'un nœud d'une macro ou d'une fonction (`n3/n7`) ramené au nœud du graph édité                                                                                                                                                                                                   | Une table rendue par les générateurs : trois générateurs à changer, pour la même information                                                                                                                                                                                                                                                    |

Une fonction : une entrée et une sortie d'exécution, sans délai ; une macro : des entrées et sorties d'exécution à elle, des délais permis. Pas de récursion | De vrais appels : une pile dans l'interpréteur et le code compilé, un état par appel, pour le même résultat                                                                                                                                                                                                                                     |

## 2. Le modèle

`engine-graph` gagne :

- **`GraphLayout`** (`layout.ts`) : `nodes` (la position de chaque nœud par id), `notes` (des textes posés sur le graph : position, taille, texte), `groups` (un cadre titré et coloré autour de nœuds, déplacés avec lui). `nodeSize(inputs, outputs)` et `portPosition(…)` : la géométrie partagée par la page et le moteur. **`autoLayout(body, ports)`** : les couches par le plus long chemin depuis les sources (arêtes d'exécution comprises, les retours ignorés), l'ordre dans une couche par la moyenne de ses prédécesseurs, deux passes.
- **Les éditions** (`edit.ts`), pures, sur un `GraphBody` : `addNode`, `removeNodes` (et leurs arêtes, leurs places dans les groupes), `connect` (remplace l'arête d'une entrée qui n'en prend qu'une), `disconnect`, `setParams`, `setDefault`, `setLabel`, `moveNodes`, `addNote`, `editNote`, `removeNote`, `groupNodes`, `editGroup`, `ungroup`, `copyFragment` et `pasteFragment` (de nouveaux ids, les arêtes internes gardées), `uniqueNodeId`.

`@fdw/engine-graph-editing` :

- **`GraphKind`** : ce que l'éditeur sait d'une sorte de graph : son format, `parse` et `serialize`, `validate` (les ports résolus de chaque nœud, leurs types en texte, les diagnostics), `templates` (le catalogue de la recherche : un type de nœud et des paramètres, « Get health » est `var.get` sur `health`), ses sous-graphs (les fonctions), `accepts`. Trois sortes : `materialGraphKind`, `animationGraphKind`, `behaviorGraphKind(registry)`.
- **`GraphSession`** : un document d'une sorte, son `History`, la portée éditée (le graph ou une de ses fonctions) ; `execute(command)` applique une `GraphCommand` (les éditions ci-dessus, `undo`, `redo`, les champs du document : variables, paramètres, fonctions) ; `projection()` : ce que la page montre ; `onChange`.
- **`GraphTarget`** : un graph d'une scène, vivant. `kind`, `name`, `graph()`, `apply(graph)`, et selon la sorte : le `Material` et son remplacement (matériaux), les `Animator` qui le jouent (animations), le `BehaviorSystem` (comportements).
- **`MaterialPreview`** : une sphère, un cube ou un plan éclairés, le matériau compilé, rendus dans une texture et relus. **`materialCode`** : le code du backend (`backend.codegen`) et sa source map (`sourceMap(code)` : les lignes de chaque nœud).
- **`inspectAnimator`** : l'état des machines, le poids de chaque nœud dans la pose (`Animator.weights()`), les paramètres.

## 3. Le protocole

Les messages `extension` (`{ type: 'extension', extension: 'fdw.graphs', message, data? }`) dans les deux sens ; `data` porte les octets (l'image de l'aperçu), que le relais de Dawn encode en base64. Une session par vue de l'éditeur (une par sorte).

| De la page                                                                  | Du moteur                                                                                  |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `targets` : la liste des graphs de la scène                                 | `targets` : à chaque scène, et quand ses graphs changent (le TPS charge ses ennemis après) |
| `open` : une session sur une cible, un fichier (son texte) ou un graph neuf | `catalog` : les modèles de nœuds de la session ; `graph` : la projection, à chaque édition |
| `command` : une `GraphCommand`                                              | `refused` : une connexion ou une commande refusée, et pourquoi                             |
| `save` : le document en JSON                                                | `file` : le texte du document                                                              |
| `preview` : la forme de l'aperçu                                            | `code` : le code généré et sa source map ; l'aperçu, son image dans `data`                 |
| `animation` : l'animator suivi, un paramètre forcé                          | `live` : l'état des machines, les poids, les paramètres (dix fois par seconde)             |
| `debug` : attacher, une instance, un point d'arrêt, continuer, pas à pas    | `debug` : l'arrêt, les états des nœuds, la trace, les variables (dix fois par seconde)     |
| `close`                                                                     |                                                                                            |

Le débogueur arrêté **gèle la scène** : l'extension le dit au moteur (`holdsScene`), qui ne dessine plus ses images ; le pas à pas fait avancer le graph sans elles.

## 4. L'interface

`@fdw/graph-editor` : `GraphCanvas`, le canevas (déplacer la vue au bouton du milieu ou droit, zoomer à la molette autour du pointeur ; sélectionner au clic, Maj, Ctrl, et au rectangle ; glisser les nœuds, les groupes ; tirer un fil d'un port à l'autre, les ports compatibles en évidence, un fil lâché dans le vide ouvre la recherche filtrée sur les nœuds qui s'y branchent ; Alt+clic sur un port le déconnecte ; Suppr, Ctrl+C, X, V, D, A, Z, Y ; F cadre la sélection, Espace ou Tab ouvre la recherche, Ctrl+F cherche un nœud du graph, N pose une note, Ctrl+G groupe) ; `NodeSearch`, la recherche (par titre, type, catégorie, description) ; `NodeInspector`, les paramètres et les valeurs des entrées non branchées du nœud actif, son libellé, ses diagnostics ; `GraphPanel`, le panneau d'un plugin : la barre (le graph ouvert, nouveau, ouvrir, enregistrer, annuler, refaire, disposer, la portée), le canevas, une colonne d'onglets que chaque plugin remplit. Un **calque** (`GraphOverlay`) donne au canevas l'état vivant : la classe d'un nœud (arrêté, actif, point d'arrêt), un badge, une barre de poids, les fils actifs, la valeur d'un port.

Les plugins :

- **Matériaux** (`fdw.materialGraph`) : l'aperçu (sphère, cube, plan ; animé), le code (WGSL, GLSL ES ou HLSL selon le backend) avec la source map : un clic sur une ligne sélectionne son nœud, les lignes du nœud actif en évidence ; les problèmes, sur les nœuds et en liste ; les paramètres du graph.
- **Animations** (`fdw.animationGraph`) : la machine à états d'un nœud `anim.stateMachine` dans une vue à elle (double clic) : les états en boîtes, les transitions en flèches, éditées dans l'inspecteur (durée, conditions, déclencheur, temps de sortie) ; pendant la lecture, l'état courant et la transition en cours, le poids de chaque nœud, les paramètres (forçables) de l'animator suivi.
- **Comportements** (`fdw.behaviorGraph`) : le débogueur à la souris (F9 sur un nœud pose un point d'arrêt, F5 continue, F10 avance d'un nœud, l'instance suivie choisie dans la liste) : le nœud arrêté, les nœuds passés pendant la dernière exécution et leurs fils, le nombre de passages et les valeurs des sorties de chaque nœud, les variables de l'instance ; les variables et les événements du graph ; les fonctions et les macros : en créer, éditer leur signature et leur corps (la portée), les appeler depuis la recherche.

## 5. Démo et validation

- **La galerie procédurale** (`procedural`) expose ses matériaux : le bois modifié dans l'éditeur, l'aperçu et la scène recompilés à chaque modification, une erreur de type refusée.
- **Le TPS** (`tps`) expose l'IA des ennemis (le `BehaviorSystem`), le graph du héros et ceux des ennemis (leurs animators) : un point d'arrêt sur `attack`, le jeu gelé quand un orc attaque, le pas à pas ; la machine du héros suivie pendant qu'il court ; la portée d'attaque des ennemis changée en jeu.
- **Les tests** : `engine-graph` (layout, éditions), `engine-graph-editing` (les commandes et l'historique, les trois sortes, les cibles, la source map, l'aperçu sur un backend factice), `engine-behavior` (`setGraph`, fonctions, macros, débogage dans un corps dépliés), `engine-animation` (`setGraph`, `weights`), `graph-editor` (le canevas dans jsdom : dessin, glissés, connexions refusées, recherche, copier-coller), les plugins avec l'hôte factice, l'extension avec une plateforme factice, l'éditeur web dans Chromium (la documentation).
- **Les tutoriels** (EN et FR, éditeur vivant) : « Éditer un matériau », « Animer dans l'éditeur », « Déboguer un comportement ».

## 6. Reporté

- Plusieurs graphs d'une même sorte ouverts à la fois (une vue par sorte) : les vues multiples de dockview, avec le projet de P20.
- Les matériaux du niveau enregistrés avec lui après édition (P20 : le projet, le catalogue) ; leur édition rejoint l'historique de la session, pas celui du niveau.
- L'aperçu d'un graph de comportement ou d'animation hors d'une scène (il faut un squelette, un jeu).
- Les points d'arrêt conditionnels, la pile d'appels des fonctions (dépliées, elles n'en ont pas).
- Une mini-carte du canevas.
