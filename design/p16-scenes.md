# P16 : les scènes et les niveaux, import et export

Enregistrer et recharger un niveau entier ([roadmap P16](roadmap.md#p16-scènes-et-niveaux--import-et-export-modulaires)) : les nœuds, les meshes et les matériaux, les lumières, les caméras, les corps et leurs formes (P7b), les sons (P7), les graphs (P6, P9) ; l'échanger en glTF ; laisser l'utilisateur ajouter ses formats et ses composants.

Ce qui existait : le système de ressources de P5 (sources montées sous des schémas et par priorité, chargeurs, `ResourceStore`, poignées, scopes, dépendances, annulation, progression), `ModelData` et `instantiate` (`engine-assets`), la lecture de glTF (`engine-gltf`), des archives zip (`ArchiveSource`), les documents JSON des trois graphs (`parseDocument`, une version exacte). Ce qui manquait :

- **Les schémas des composants** ne donnaient que les types des champs : ni valeurs par défaut, ni version, ni nom stable (l'identifiant d'un composant est son rang d'enregistrement), et le `World` ne permettait pas de les énumérer.
- **Des composants tiennent des objets vivants** : `light`, `camera view`, `mesh renderer` (un `Mesh` et un `Material` sur le GPU), `physics body` (le corps Rapier, sa description perdue), `audio emitter` (des voix). Les comportements sont hors de l'ECS. `node state` mêle données et état d'exécution.
- **Les nœuds ne savaient pas d'où ils viennent** : `instantiate` ne gardait ni le modèle ni son URI ; un `Mesh` ou un `Material` n'a qu'un `label`.
- **Rien n'écrivait** : pas d'écrivain glTF dans les packages (seulement l'outil Node `tools/assets/gltf.mjs`), pas d'écriture dans les sources.
- **Le niveau du TPS était construit en code** (`createTpsScene`, `buildForest`, tirages à graine), aucun fichier.

## 1. Les choix

| Question                             | Choix                                                                                                                                                                                                                                                                    | Écartés, et pourquoi                                                                                                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Le package                           | **`@fdw/engine-scene-io`**, sur `engine-scene`, `engine-resources`, `engine-assets` ; les codecs de la physique, du son et des comportements dans leurs packages (`physicsCodec`, `soundEmitterCodec`, `behaviorCodec`), le glTF dans `engine-gltf`                      | Dans `engine-scene`, qui ne connaît pas les ressources ; un package qui dépend de tous les autres : un jeu sans physique l'embarquerait                               |
| La représentation pivot              | **`SceneData`** : neutre, sur le CPU, comme `ModelData`. | Les instances et les préfabriqués    | **Une scène est une ressource** (`SceneDataType`), instanciable comme un modèle ; un glTF aussi. Une instance : sa source, son transform, des **surcharges par chemin de nœud**. Les éditer et les reporter dans la source : P20                                         | Tout reporter à P20 : le format changerait après ; des copies : le niveau répète la même lampe                                                                        |

## 2. `SceneData`

`nodes` (`SceneNodeData` : `name`, `position`, `rotation`, `scale`, `visible`, `static`, `occluder`, `layers`, les valeurs par défaut omises ; `parent`, un indice antérieur ; `parentPath`, sous un nœud de l'instance `parent` ; `instance` ; `components`, par nom `{ version, data }`), `batches` (`SceneBatchData`), `meshes` et `materials` écrits avec la scène (`#mesh/n`, `#material/n`). Une référence (`ResourceRef`) : une URI, ou `{ uri, options }` (une texture et son espace de couleur). Les données des composants peuvent tenir des tableaux typés (un heightfield).

## 3. Écrire et lire

- **`captureScene(scene, { store, codecs, root, uri, instances, batchMin, warn })`** : `SceneWriter` écrit les champs et les composants ; une ressource du store par son URI relative à `uri`, sauf les sous-ressources d'un fichier de scène (réécrites avec la scène enregistrée) ; les autres meshes et matériaux avec la scène. `instances: 'expand'` écrit les nœuds des instances comme les autres (pour glTF).
- **`instantiateScene(data | handle, scene, { store, parent, codecs, uri, wrap, signal, warn })`** : les modèles et les scènes des instances chargés ensemble, les nœuds dans l'ordre, les lots, puis les composants phase par phase (`codec.phase`, `lod` en phase 1). Une scène en mémoire : ses meshes et matériaux définis dans le store le temps de l'instance. `wrap: false` : les nœuds directement sous le parent (les corps qui mènent leur nœud doivent être sous la racine). Annulée, l'instance retire ce qu'elle a fait.
- **Les instances** : un modèle (`model instance`, ses entités avec leur génération) ou une scène chargée par le store (`scene instance`, ses nœuds et ce qu'ils étaient une fois faits, écrits en URI canoniques : la base des surcharges). Les surcharges : les champs et les composants qui diffèrent, ou `removed`, par chemin (`modelPaths`, `scenePaths` : les noms, `#k` quand ils se répètent, `nom#i` pour la primitive i).

## 4. Les codecs

`ComponentCodec { name, version, phase?, has?, write, read, migrate? }`. `WriteContext` : `resource`, `mesh`, `material`, `indexOf`, `warn`. `ReadContext` : `load`, `mesh`, `material`, `entity`, `service`, `warn`.

| Codec                      | Package           | Données                                                                                      |
| -------------------------- | ----------------- | -------------------------------------------------------------------------------------------- |
| `meshRendererCodec`        | `engine-scene-io` | Mesh et matériau par référence, `castShadow`                                                 |
| `lightCodec`               | `engine-scene-io` | La lumière du moteur telle quelle (ambiante, diffuse, spéculaire, atténuation, cône, ombres) |
| `cameraViewCodec`          | `engine-scene-io` | La projection                                                                                |
| `lodCodec(lods)`           | `engine-scene-io` | Les niveaux : les renderers en indices, les distances                                        |
| `numericCodec`             | `engine-scene-io` | Les composants de nombres `persist: true`, champ par champ                                   |
| `physicsCodec(physics)`    | `engine-physics`  | `NodeBodyDesc` ou `CharacterDesc`, sans les `userData`                                       |
| `soundEmitterCodec(audio)` | `engine-audio`    | `SoundEmitterDesc` : la source par URI (clip ou flux), bus par nom, options, `autoplay`      |
| `behaviorCodec(systems)`   | `engine-behavior` | Par graph, les variables ; celles de type `entity` en indices                                |

La conversion couleur × intensité des lumières est celle de glTF seulement ; le format du moteur garde la lumière exacte. Les animators restent au code des personnages (squelette du modèle, clips) ; leurs graphs sont des ressources (`AnimationGraphType`), comme ceux des comportements (`BehaviorGraphType`) et des matériaux (`MaterialGraphType`, enregistré par `installAssets`).

## 5. Le format `fdw-scene` et glTF

- **`writeFdwScene(data, path, { binary, indent })`** : le JSON (`format`, `schemaVersion`, `buffers`, les graphs des matériaux une fois dans `graphs`) et le `.bin` ; chaque tableau typé devient `{ "$binary": { type, byteOffset, length } }`, aligné sur 8 octets ; `binary: 'embedded'` le met en base64 dans le JSON. **`fdwSceneLoader`** (`installSceneIo`) fournit les meshes et matériaux comme sous-ressources du fichier. `migrateFdwScene` et `fdwSceneMigrations`.
- **glTF** (`engine-gltf`) : `installGltfScenes` charge `.gltf` et `.glb` en `SceneDataType` (nœuds, primitives, lumières, caméras, corps et formes, `EXT_mesh_gpu_instancing` en lots, composants de `FDW_scene`) ; `writeGltf(data, path, { store, uri, binary, warn })` écrit le `.glb` (ou `.gltf` et `.bin`) : meshes désentrelacés, images copiées sans réencodage, lumières en couleur et intensité, lots en `EXT_mesh_gpu_instancing`, corps en KHR (un heightfield en maillage, avec un avertissement). Ce que glTF ne sait pas dire (le graph d'un matériau, la lumière exacte, la forme exacte, les autres composants) va dans `FDW_scene` : le moteur relit le fichier sans perte. Le crochet `material` des extensions accepte toute `MaterialData` et peut être asynchrone. Validé par `gltf-validator` (Khronos) dans les tests.
- **`ZipReader`** : `maxEntries` (65 535), `maxEntrySize` (1 Gio), `maxTotalSize` (4 Gio), et une entrée n'est jamais décompressée au-delà de la taille qu'elle déclare.

## 6. Le niveau du TPS

- `buildForest` construit la forêt sous un nœud `forest` : le nœud `terrain` (composant `tps terrain` : le terrain, son matériau de sol, ses options ; son heightfield), les lots des sapins, herbes et fougères avec leurs niveaux, les nœuds `trunk` et leurs capsules, et le composant `tps forest` (les troncs, le rayon de jeu). Leurs codecs dans `tps/level.ts` (`levelCodecs`) : l'exemple d'un jeu qui écrit les siens.
- `tools/assets/make-tps-level.ts` la construit une fois (backend de test, Rapier pour les descriptions) et l'écrit à côté des modèles : `forest/forest.scene.json` (928 Kio, compact) et `forest.scene.bin` (1,6 Mio). `--gltf` l'écrit aussi en glTF (21 Mio), le terrain en maillage, sans erreur au validateur.
- Le jeu la charge (`createTpsScene({ level: TpsLevelPath })`, démo web, documentation, démo native) ; la roche cuite au démarrage est définie sous `generated/rock.texture` (`defineRock`).
- **Rejoué à l'identique** (test) : des boules lâchées sur la forêt construite et sur la forêt rechargée, 240 pas de Rapier, les mêmes positions au bit près.

## 8. Reportés

- **Le projet** (plusieurs scènes, le catalogue tenu à jour à l'import et aux déplacements de fichiers, les réglages d'export) : l'éditeur de jeu, P20 ; la `CatalogSource` en est la base. Les fichiers relatifs d'un asset de catalogue se lisent depuis la racine de la source : préférer les `.glb`.
- **Les surcharges des instances imbriquées** (un modèle dans un préfabriqué) et l'édition des surcharges, leur report dans la source : P20.
- **Le package de jeu** (`.fdwgame` : un zip, son manifeste, les dépendances collectées depuis le graphe du store) : P11. La lecture marche (`ArchiveSource`) ; il manque l'écrivain zip et la collecte.
- Les animators en composants, avec leur codec : quand un personnage sera fait dans l'éditeur (P20).
- Un corps qui mène un nœud sous un parent autre que la racine (ScenePhysics le refuse : `wrap: false` en attendant).
- Le `volume` des renderers (requêtes exactes) n'est pas écrit.
- L'écriture dans les sources (enregistrer en place) : P18. Les sources distantes et le chargement par morceaux. Un format binaire, si les mesures le demandent.
- Le rejeu entre web et natif (même version de Rapier, autre plateforme) : non vérifié.
